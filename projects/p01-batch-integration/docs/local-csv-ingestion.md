# Local CSV ingestion adapters

## Purpose

This module provides the concrete local infrastructure adapters required to
execute the P01 batch-ingestion workflow against CSV files and an immutable
filesystem landing zone.

The adapters implement the application ports defined by P01 without coupling
the domain or application layers to filesystem, CSV or operating-system
details.

They provide a production-oriented local execution baseline and deterministic
behavior suitable for development, integration testing and controlled
on-premises ingestion.

## Components

### `LocalCsvArtifactInspector`

Inspects a local CSV artifact through an absolute `file://` URI.

Responsibilities:

- Resolve and validate the source path beneath an explicitly allowed root.
- Reject missing files, directories and paths escaping the allowed root.
- Reject symbolic links resolving outside the trusted source root.
- Read the artifact as strict UTF-8 with optional UTF-8 BOM support.
- Process the source incrementally without loading the complete file into RAM.
- Calculate the SHA-256 digest and byte size from the original bytes.
- Count logical CSV records while supporting quoted multiline fields.
- Validate that headers are present, nonblank and unique.
- Validate that every data row has the expected number of columns.
- Detect source-file changes occurring during inspection.
- Return immutable artifact metadata through the application port.

Blank physical rows are ignored and are not counted as business records.

### `LocalFilesystemLandingStore`

Copies an inspected source artifact into an immutable local landing zone.

Responsibilities:

- Resolve source paths beneath the configured trusted source root.
- Validate destination object keys and reject absolute or traversing paths.
- Reject intermediate symbolic-link escapes from the landing root.
- Stream the source into a temporary file while recalculating its checksum and
  byte size.
- Compare the copied content against the metadata produced by inspection.
- Flush file contents before publication.
- Apply restricted `0640` permissions to landed artifacts.
- Publish through an atomic no-overwrite filesystem operation.
- Synchronize the destination directory after publication.
- Verify and reuse an existing identical artifact during retries.
- Reject an existing destination containing different bytes.
- Reject directories, symbolic links and other nonregular destinations.
- Remove temporary files after success or controlled failure.

## Trust boundaries

The source and landing roots are explicit security boundaries.

A source URI is accepted only when it identifies an absolute local file and
resolves beneath the configured source root. Remote file authorities, query
parameters, fragments and unsupported URI schemes are rejected.

A landing object key is always interpreted relative to the landing root.
Absolute paths, empty path segments, parent traversal and intermediate
symbolic-link escapes are rejected.

The final destination is inspected without following symbolic links before an
existing object is accepted as an idempotent retry.

These controls reduce accidental path traversal and symbolic-link attacks.
Filesystem ownership and operating-system permissions must still restrict
untrusted users from modifying the configured roots.

## Immutability and concurrency

Landing objects are addressed with the deterministic key generated by the
application layer.

Publication never overwrites an existing object:

1. Source bytes are copied and verified in a temporary file.
2. The temporary artifact is synchronized and assigned restricted permissions.
3. An atomic no-overwrite operation publishes the destination.
4. If another worker wins the race, the winning artifact is verified.
5. Identical content is treated as a successful retry.
6. Different content raises an immutable landing conflict.

This provides safe behavior for normal retries and concurrent workers sharing
the same local filesystem.

The guarantees apply only when the temporary and destination paths use a
filesystem supporting the required atomic link and synchronization semantics.

## Integrity model

The inspector produces:

- Source file name.
- Content type.
- Record count.
- Byte size.
- SHA-256 digest.

The landing adapter independently recalculates byte size and SHA-256 while
copying. A mismatch prevents publication.

The application service verifies the returned landing receipt before creating
the batch registration. The same digest participates in the deterministic
idempotency key and immutable object key.

## Failure model

Infrastructure failures are exposed as controlled adapter exceptions:

- `LocalArtifactAccessError`: the source cannot be accessed safely.
- `CsvArtifactValidationError`: CSV encoding or structure is invalid.
- `LocalArtifactIntegrityError`: copied bytes differ from inspected metadata.
- `ImmutableLandingConflictError`: an immutable destination is unsafe or
  contains incompatible bytes.

The adapters do not silently reinterpret malformed input and do not overwrite
conflicting data.

## Testing

The automated suite covers:

- UTF-8 BOM and multiline CSV records.
- Configurable delimiters.
- Empty, duplicate and malformed headers.
- Invalid row widths and invalid encodings.
- Missing files, directories and unsafe source URIs.
- Source-root and symbolic-link containment.
- Streaming checksum, byte-size and record-count calculation.
- Atomic landing with restricted permissions.
- Checksum mismatch cleanup.
- Unsafe object keys and landing-root escapes.
- Directory and symbolic-link destinations.
- Idempotent retries.
- Conflicting immutable destinations.
- Concurrent publication attempts.
- End-to-end inspection, landing, registration and retry deduplication.

All tests run through the P01 quality gate with formatting, static analysis,
strict typing, coverage enforcement and Python compilation.

## Operational boundaries

This change does not yet provide:

- A command-line or HTTP entrypoint.
- PostgreSQL-backed batch registration.
- Transactional outbox event publication.
- Google Cloud Storage landing.
- Encryption-key or retention-policy management.
- Cross-host filesystem coordination.

Those capabilities belong to subsequent adapters and delivery changes. The
domain and application contracts remain independent of those implementations.
